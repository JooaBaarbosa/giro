# Giro MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Dashboard de estoque para pequeno comércio que sugere pedidos de compra para itens abaixo do mínimo e, após aprovação do dono, envia o pedido ao fornecedor via WhatsApp (n8n + Meta Cloud API, com dry-run).

**Architecture:** API FastAPI (fonte da verdade, regras numa camada de serviço) servindo JSON em `/api/*` e telas HTMX/Jinja em `/`; PostgreSQL com livro-razão de movimentações; n8n só orquestra — chama a API, envia WhatsApp, devolve callbacks. Tudo sobe com `docker compose up`.

**Tech Stack:** Python 3.14, uv, FastAPI, SQLAlchemy 2 (síncrono) + psycopg 3, Alembic, pydantic-settings, Jinja2, HTMX 2.0.4, Chart.js 4.4.7, Pico CSS 2.0.6, httpx, python-json-logger, pytest + testcontainers, ruff, mypy, PostgreSQL 17, n8n (imagem com tag fixa).

**Spec:** `docs/superpowers/specs/2026-10-22-giro-design.md`

## Global Constraints

- `pyproject.toml`: `requires-python = ">=3.14,<3.15"`; `.python-version`: `3.14.8`. Gerenciador: `uv`.
- Interface e mensagens ao usuário em pt-BR; código, tabelas, colunas e enums em inglês.
- Status de pedido no banco: `suggested`, `approved`, `sending`, `sent`, `received`, `failed`, `cancelled`.
- Quantidades: `NUMERIC(12,3)` / `Decimal` em todo o código (nunca `float`).
- Fuso para "hoje"/"mês": `STORE_TZ`, padrão `America/Sao_Paulo`. `occurred_at` é `timestamptz`.
- `WHATSAPP_DRY_RUN` padrão `true`. Timeout de `sending`: 10 min. Timeout do webhook n8n: 3 s. Cron do WF1: 15 min.
- Todas as rotas `/api/*` exigem `X-Service-Token` (401 sem ele). Decisão do plano: a spec exige isso nas rotas de automação; estendemos para todo `/api/*` porque é a porta de entrada futura de PDV/planilha. Rotas web (`/`) ficam sem autenticação (limitação documentada).
- Mapeamento de erros: `InvalidInput`/`DuplicateSku` → 422; `InsufficientStock`/`InvalidTransition`/`EmptyOrder` → 409; `NotFound` → 404.
- Texto exato das mensagens de erro de domínio (exibidas na tela):
  - `InsufficientStock`: `"Estoque insuficiente: disponível {disp}, solicitado {qtd}."`
  - `InvalidTransition`: `"Pedido não pode passar de {de} para {para}."`
  - `EmptyOrder`: `"Pedido sem itens não pode ser aprovado."`
  - timeout de envio: `"envio não confirmado; verifique antes de reenviar"`
- Desvio consciente da spec: o envio ao WhatsApp no n8n usa **nó HTTP Request** para a Graph API (não o nó nativo), porque a spec exige credencial vinda de variável de ambiente e o nó nativo exige credencial armazenada no n8n.

## Review Focus

1. **Quantidade fracionada em produto `un`/`cx`** (ex.: vender 1,5 un) → recusada com 422 "Quantidade deve ser inteira para unidade un." — teste na Task 4.
2. **Venda perto da meia-noite**: venda às 23:30 de São Paulo (02:30 UTC do dia seguinte) conta no dia de São Paulo, tanto em "saída hoje" quanto no gráfico — teste na Task 5.
3. **Telefone digitado com formatação** (`+55 (11) 98765-4321`) → aceito e normalizado para `+5511987654321`; sem `+`/DDI → 422 — teste na Task 4.
4. **Duplo clique em Aprovar** → segundo clique mostra mensagem amigável de transição inválida e o webhook do n8n é chamado só uma vez — teste na Task 10.
5. **Editar item do pedido para 0, negativo ou fracionado em `un`** → 422, item inalterado — teste na Task 6.

### Task 2: Previsão (`forecast.py`)

**Files:**
- Create: `src/giro/forecast.py`, `tests/unit/test_forecast.py`

**Interfaces:**
- Consumes: `models.Unit`
- Produces:

```python
@dataclass(frozen=True)
class Forecast:
    avg_daily: Decimal
    days_left: Decimal | None      # None quando no_forecast
    next_purchase: date | None     # None quando no_forecast
    suggested_qty: Decimal
    low_history: bool
    no_forecast: bool

def compute_forecast(*, current_stock: Decimal, min_stock: Decimal, cover_days: int,
                     unit: Unit, sales_by_day: Mapping[date, Decimal],
                     first_sale: date | None, today: date) -> Forecast
```

Algoritmo (fixado aqui porque a spec deixa a janela implícita):
- `window = min(30, (today - first_sale).days + 1)` se `first_sale` não é None; senão `window = 1`.
- `total = soma de sales_by_day[d]` para `d` em `[today - window + 1, today]`.
- `no_forecast = total == 0`; `avg_daily = total / window` (0 se no_forecast).
- Se não no_forecast: `days_left = (current_stock - min_stock) / avg_daily`; `next_purchase = today` se `days_left <= 0`, senão `today + timedelta(days=floor(days_left))`.
- `raw = avg_daily * cover_days + min_stock - current_stock`; `un`/`cx`: `ceil(raw)`; `kg`: arredonda para cima com 1 casa (`ROUND_CEILING` em `Decimal("0.1")`); depois `max(resultado, 1)`.
- `low_history = window < 7` (apenas se não no_forecast).

@dataclass(frozen=True)
class ProductRow:

    forecast: Forecast; status: StockStatus
